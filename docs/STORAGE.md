# 저장·백업·서버 활성화 검토

## 브라우저 데이터 보존

현재 기본 저장은 IndexedDB v1이다. 기존 프로젝트·대화·맥락·업무·파일을 삭제하거나 ID를 바꾸지 않는다. 새 컬렉션은 기존 v1에 빈 배열로 보충한다. 브라우저 주소별 저장 공간이 다르므로 이전 URL의 설정에서 백업을 먼저 내보낸다.

설정 → 백업: 기본은 현재 영역, 전체 영역은 직접 선택. 원본 포함 여부를 확인한다. 큰 파일은 영역별/원본 제외 백업을 선택한다(원본 합계 45 MB, 백업 64 MB 제한). 가져오기는 범위·새 항목·충돌·원본 수를 표시하고 확인 후 병합한다. 기존 항목 우선이며 같은 ID의 다른 파일은 덮어쓰지 않는다. 파일 없는 메타데이터 백업은 원본 파일까지 복원하지 않는다.

## 준비한 서버 구조

- `supabase/migrations/202610140001_workspace.sql`: 소유자+영역별 JSON 스냅샷, RLS, 인증된 RPC 저장, row lock+revision 비교, 사설 파일 버킷/정책. 익명 조회/저장 금지, 서비스 역할 키를 앱에서 사용하지 않음.
- `/api/workspace`: 인증된 사용자에 대해 회사/개인 영역을 명시해서 GET/PUT. 누락/혼합 영역은 거부. 전체 영역 조회 API 없음.
- `/api/workspace/search`, `/api/assistant/answer`: 같은 사용자·영역·프로젝트의 자료만 근거로 조회. 후자는 모델 연결 전 501이며 답변을 가장하지 않는다.
- `/api/workspace/files`: 소유자/영역/메타데이터 검증 후 사설 원본 전송. insert-only, 동일 바이트 재시도는 허용하고 다른 원본 덮어쓰기는 거부.
- `JARVIS_CLOUD_STORAGE_ENABLED=true`일 때만 활성화한다. 설정은 비밀값이나 토큰 입력란을 제공하지 않는다. 기존 Supabase public URL/publishable key와 검증된 앱 계정 세션이 필요하다. Vercel 로그인은 앱 계정을 대신하지 않는다.

서버 자료 검토 → 충돌 기준/자료 확인 → 이 기기에 병합 → 현재 영역 서버 저장 순서다. 예상 revision이 달라지면 409를 반환하므로 다른 기기 변경을 조용히 덮어쓰지 않는다. 삭제 동기화나 백그라운드 자동 업로드는 제공하지 않는다. 파일 업로드가 실패해도 로컬 원본은 유지하고 실패 개수를 표시한다.

## 별도 승인이 필요한 운영 단계

현재 작업은 운영 스키마·인증·환경 변수를 변경하지 않았다. 다음은 검토 가능한 변경안이며 자동 실행하지 않는다.

1. 개인용 앱 계정을 어떤 방식으로 식별할지 결정(기존 '로그인 화면 불필요' 선호 고려). 기기 간 공유에는 검증 가능한 동일 사용자 인증이 필요하다. 현재 브라우저 캐시는 계정이 없는 개인용 저장이므로, 운영 계정 전환을 제공할 때에는 계정별 캐시 분리/세션 변경 처리도 함께 구현·검증한다.
2. 운영 백업 후 SQL 마이그레이션과 RLS/사설 파일 정책을 검토·적용한다.
3. 앱 계정 세션 연결과 플래그를 활성화하고, 설정에서 기존 브라우저 데이터를 명시적으로 이관한다.
4. 두 실제 기기에서 로그인·회사/개인 분리·충돌·파일 업로드/다운로드를 검증한 후 배포를 결정한다.

## 검증 범위

`npm run test:server`는 URL을 `http://127.0.0.1:54321`로 제한한 로컬 Supabase에서 실제 Auth/RLS/RPC/서버 조회를 검증한다. 임시 합성 사용자를 만들고 해당 사용자만 정리한다. 두 계정과 같은 계정의 두 세션, 별도 Chromium 프로필을 사용한다. 실제 두 물리 기기·운영 인증·운영 DB·실서비스 동기화는 검증하지 않았다. 로컬 slim stack에 storage-api가 없어 서버 파일 원본 API도 별도 검증이 필요하다. 브라우저 파일 원본·백업 이관은 별도 Playwright에서 검증한다.

## 2026-10-15: 프로젝트가 사라져 보일 때

같은 주소·기기·브라우저에서도 새 프로젝트가 사라진다는 보고를 조사 중이다([Issue #4](https://github.com/kjd1374/jarvis/issues/4)). 운영 주소의 별도 합성 Chromium 프로필에서는 화면 이동·새로고침 3회·브라우저 종료/재시작 후 보존됐다. 사용자의 실제 브라우저 저장 공간을 조회하지 않았으므로 실제 소실 원인이나 기존 번역 프로젝트 복구 여부는 확인하지 못했다. 주소/영역 차이로 원인을 단정하지 않는다.

확인된 결함은 프로젝트·업무의 초기 읽기 실패를 빈 목록처럼 표시하던 동작이다. 이제 로딩/오류/정상 빈 상태를 구분하며, 실패 시 생성 버튼을 막고 재조회·설정의 저장 진단을 안내한다. 이미 읽은 자료는 재조회 실패 시 유지한다.

기존 DB 이름·v1·원본 파일·항목 ID를 유지한다. 새 저장부터 `workspace` 저장소의 `last-confirmed` 키에 정상 메타데이터 스냅샷과 시각을 현재 기록/파일과 같은 트랜잭션에 보관한다. strict durability로 커밋된 후에만 저장 성공을 알린다. 정상본 저장에 실패해도 전체 저장을 취소한다. 현재 기록이 없지만 정상본이 있으면 신규 빈 업무실로 취급하거나 그 위에 저장하지 않는다.

설정 → **브라우저 저장 진단과 복구**에서 현재 주소·읽기 상태·정상본 시각·영역별 프로젝트 수를 확인한다. 현재 기록이 없거나 읽을 수 없고 정상본이 있을 때만 회사/개인 전체 복구 범위를 확인한 후 복구할 수 있다. 복구 직전 같은 쓰기 트랜잭션에서 정상 기록 존재를 다시 확인하며, 다른 탭의 정상 저장은 덮어쓰지 않는다. 읽지 못한 현재 값은 별도 키로 보존하고 파일 원본을 삭제하지 않는다.

정상본은 같은 브라우저의 중복 사본이며 서버 백업이나 이력 보관이 아니다. 전체 브라우저 저장 공간 삭제·격리된 프로필·이전 버전에서 이미 소실된 기록은 복구하지 못한다. 정상본이 없는 구버전 v1도 그대로 읽으며 다음 성공한 저장부터 정상본을 만든다. 운영 서버 저장·인증·권한은 변경하지 않았다. 안정적인 기기 간 보관은 위의 계정 식별/서버 활성화 결정이 여전히 필요하다.
