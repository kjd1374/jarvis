# 저장·백업·서버 활성화 검토

## 브라우저 데이터 보존

현재 기본 저장은 IndexedDB v1이다. 기존 프로젝트·대화·맥락·업무·파일을 삭제하거나 ID를 바꾸지 않는다. 새 컬렉션은 기존 v1에 빈 배열로 보충한다. 브라우저 주소별 저장 공간이 다르므로 이전 URL의 설정에서 백업을 먼저 내보낸다.

설정 → 백업: 기본은 현재 영역, 전체 영역은 직접 선택. 원본 포함 여부를 확인한다. 큰 파일은 영역별/원본 제외 백업을 선택한다(원본 합계 45 MB, 백업 64 MB 제한). 가져오기는 범위·새 항목·충돌·원본 수를 표시하고 확인 후 병합한다. 기존 항목 우선이며 같은 ID의 다른 파일은 덮어쓰지 않는다. 파일 없는 메타데이터 백업은 원본 파일까지 복원하지 않는다.

## 준비한 서버 구조

- `supabase/migrations/202610140001_workspace.sql`: 소유자+영역별 JSON 스냅샷, RLS, 인증된 RPC 저장, row lock+revision 비교, 사설 파일 버킷/정책. 익명 조회/저장 금지, 서비스 역할 키를 앱에서 사용하지 않음.
- `/api/workspace`: 인증된 사용자에 대해 회사/개인 영역을 명시해서 GET/PUT. 누락/혼합 영역은 거부. 전체 영역 조회 API 없음.
- `/api/workspace/search`, `/api/assistant/answer`: 같은 사용자·영역·프로젝트의 자료만 근거로 조회. 후자는 모델 연결 전 501이며 답변을 가장하지 않는다.
- `/api/workspace/files`: 소유자/영역/메타데이터 검증 후 사설 원본 전송. insert-only, 동일 바이트 재시도는 허용하고 다른 원본 덮어쓰기는 거부.
- `JARVIS_CLOUD_STORAGE_ENABLED=true`일 때만 활성화한다. 설정은 비밀값이나 토큰 입력란을 제공하지 않는다. 기존 Supabase public URL/publishable key와 검증된 앱 계정 세션이 필요하다. Vercel 로그인은 앱 계정을 대신하지 않는다.

서버 자료 검토 → 충돌 기준/자료 확인 → 이 기기에 병합 → 현재 영역 서버 저장 순서다. 예상 revision이 달라지면 409를 반환하므로 다른 기기 변경을 조용히 덮어쓰지 않는다. 삭제 동기화나 백그라운드 자동 업로드는 제공하지 않는다. 파일 업로드가 실패해도 로컬 원본은 유지하고 실패 개수를 표시한다.

## 별도 승인이 필요한 운영 단계

현재 작업은 운영 스키마·인증·환경 변수를 변경하지 않았다. 다음은 검토 가능한 변경안이며 자동 실행하지 않는다.

1. 개인용 앱 계정을 어떤 방식으로 식별할지 결정(기존 '로그인 화면 불필요' 선호 고려). 기기 간 공유에는 검증 가능한 동일 사용자 인증이 필요하다. 현재 브라우저 캐시는 계정이 없는 개인용 저장이므로, 운영 계정 전환을 제공할 때에는 계정별 캐시 분리/세션 변경 처리도 함께 구현·검증한다.
2. 운영 백업 후 SQL 마이그레이션과 RLS/사설 파일 정책을 검토·적용한다.
3. 앱 계정 세션 연결과 플래그를 활성화하고, 설정에서 기존 브라우저 데이터를 명시적으로 이관한다.
4. 두 실제 기기에서 로그인·회사/개인 분리·충돌·파일 업로드/다운로드를 검증한 후 배포를 결정한다.

## 검증 범위

`npm run test:server`는 URL을 `http://127.0.0.1:54321`로 제한한 로컬 Supabase에서 실제 Auth/RLS/RPC/서버 조회를 검증한다. 임시 합성 사용자를 만들고 해당 사용자만 정리한다. 두 계정과 같은 계정의 두 세션, 별도 Chromium 프로필을 사용한다. 실제 두 물리 기기·운영 인증·운영 DB·실서비스 동기화는 검증하지 않았다. 로컬 slim stack에 storage-api가 없어 서버 파일 원본 API도 별도 검증이 필요하다. 브라우저 파일 원본·백업 이관은 별도 Playwright에서 검증한다.

## 2026-10-15: 프로젝트가 사라져 보일 때

같은 주소·기기·브라우저에서도 새 프로젝트가 사라진다는 보고를 조사 중이다([Issue #4](https://github.com/kjd1374/jarvis/issues/4)). 운영 주소의 별도 합성 Chromium 프로필에서는 화면 이동·새로고침 3회·브라우저 종료/재시작 후 보존됐다. 사용자의 실제 브라우저 저장 공간을 조회하지 않았으므로 실제 소실 원인이나 기존 번역 프로젝트 복구 여부는 확인하지 못했다. 주소/영역 차이로 원인을 단정하지 않는다.

확인된 결함은 프로젝트·업무의 초기 읽기 실패를 빈 목록처럼 표시하던 동작이다. 이제 로딩/오류/정상 빈 상태를 구분하며, 실패 시 생성 버튼을 막고 재조회·설정의 저장 진단을 안내한다. 이미 읽은 자료는 재조회 실패 시 유지한다.

기존 DB 이름·v1·원본 파일·항목 ID를 유지한다. 새 저장부터 `workspace` 저장소의 `last-confirmed` 키에 정상 메타데이터 스냅샷과 시각을 현재 기록/파일과 같은 트랜잭션에 보관한다. strict durability로 커밋된 후에만 저장 성공을 알린다. 정상본 저장에 실패해도 전체 저장을 취소한다. 현재 기록이 없지만 정상본이 있으면 신규 빈 업무실로 취급하거나 그 위에 저장하지 않는다.

설정 → **브라우저 저장 진단과 복구**에서 현재 주소·읽기 상태·정상본 시각·영역별 프로젝트 수를 확인한다. 현재 기록이 없거나 읽을 수 없고 정상본이 있을 때만 회사/개인 전체 복구 범위를 확인한 후 복구할 수 있다. 복구 직전 같은 쓰기 트랜잭션에서 정상 기록 존재를 다시 확인하며, 다른 탭의 정상 저장은 덮어쓰지 않는다. 읽지 못한 현재 값은 별도 키로 보존하고 파일 원본을 삭제하지 않는다.

정상본은 같은 브라우저의 중복 사본이며 서버 백업이나 이력 보관이 아니다. 전체 브라우저 저장 공간 삭제·격리된 프로필·이전 버전에서 이미 소실된 기록은 복구하지 못한다. 정상본이 없는 구버전 v1도 그대로 읽으며 다음 성공한 저장부터 정상본을 만든다. 운영 서버 저장·인증·권한은 변경하지 않았다. 안정적인 기기 간 보관은 위의 계정 식별/서버 활성화 결정이 여전히 필요하다.

## 2026-10-15: 승인된 로그인 없는 기기 연결 전환

사용자는 서버 저장을 승인한 뒤 이메일·로그인 화면은 제외하라고 정정했다. 이번 구현은 로그인/가입/이메일/비밀번호 입력 없이 **기기 세션**을 유지한다. Supabase의 내부 기기 사용자 식별만으로 자료 접근을 허용하지 않는다. 설정에 표시되는 12자리 기기 확인 번호는 요청 식별자이며 인증 비밀값이 아니다. 사용자가 현재 작업에서 확인한 번호만 기존 관리 권한으로 등록한다. 최초 방문자가 업무실을 선점할 수 없다.

- `jarvis_installation`: 단일 업무실 UUID. 개별 기기 사용자 삭제와 독립되어 업무 기록이 연쇄 삭제되지 않는다.
- `jarvis_devices`: 기기 세션 사용자, 확인 요청 번호, 생성/승인/해제 시각. 일반 사용자 역할은 승인 값을 변경하거나 다른 기기를 조회할 수 없다.
- `jarvis_current_owner()`/RLS/저장 RPC/사설 파일: 승인되고 해제되지 않은 현재 기기만 같은 업무실 UUID에 접근한다. `jarvis_spaces.owner_id`는 이제 이 업무실 UUID를 참조한다. 회사/개인 API 요청은 계속 각각 명시한다.
- 쿠키는 HttpOnly/SameSite=Lax, 운영 HTTPS에서 Secure다. 웹 앱에 관리 토큰이나 service-role 키를 넣지 않는다. 기기 연결 해제는 DB의 기기 권한을 해제하고 세션 쿠키를 지운다. 새 브라우저/쿠키 삭제 후에는 다시 기기를 확인한다.
- `202610150001_device_access.sql`은 기존 업무 행이 남아 있으면 중단한다. 기존 행을 조용히 이관/삭제하지 않는다. `202610150002_device_revocation.sql`은 기기의 즉시 접근 해제를 제공한다.

연결된 기기의 변경은 서버 자동 저장 대상이다. 같은 트랜잭션에서 기기별 사본과 전송 대기 세대를 보관한 후 서버 revision을 비교해 전송한다. 완료/전송 대기/실패/충돌을 화면에서 구분한다. 실패한 대기는 새로고침 후에도 남고, 서버에 같은 내용이 이미 있다면 응답 유실로 중복 저장하지 않는다. 다른 기기의 변경과 충돌하면 양쪽 자료를 유지하고 상세 확인·기준 선택 후에만 병합한다. 검토 중 변경이 생기면 다시 확인해야 한다.

### 2026-10-15: 실행기 갱신 중 저장 충돌 복구 (Issue #21)

영역별 마지막 서버 확인본을 기기별 IndexedDB의 `cloud-sync.bases`에 추가한다. 기존 DB 버전·원본·저장 대기는 그대로 읽으며 서버 테이블은 변경하지 않는다. 기준본·현재 입력·최신 서버를 비교해 서로 다른 필드/항목의 변경과 새 요청 ID를 함께 저장한다. 같은 필드를 양쪽에서 수정했거나 삭제와 수정이 겹친 경우에만 검토한다. 프로젝트 편집기의 비어 있는 선택 항목은 미설정과 같은 값으로 취급한다. 오래된 실행 상태/임대/결과를 합성하거나 재생하지 않으며, 최신 서버 관찰값과 충돌한 실행 기록은 서버 값을 유지한다.

검토 선택은 사용자가 본 값에 적용한 뒤 이후 서버 변경과 다시 비교한다. 접속 시각이나 별도 기록의 추가 때문에 재확인을 요구하지 않는다. 선택한 내용과 새 편집이 실제로 겹치면 확인을 해제하고 새 비교를 표시한다. 기존 버전에서 남은 대기에 기준본이 없으면 한 번의 명시적 검토를 유지한다. 같은 ID 안의 새 요청과 서로 다른 항목을 합치므로 서버 우선 선택이 모든 기기 입력을 버리는 동작은 아니다.

조건부 저장(CAS)은 계속 서버에서 검사한다. 전송 사이에 버전이 바뀌면 최신 서버를 다시 읽고 최대 5회 재계산하며, 계속 경쟁하면 대기를 보존한 재시도 상태로 남긴다. 응답 대기 중 추가 입력은 원자적 로컬 트랜잭션에서 다시 합치고 새 대기 세대를 지우지 않는다. 저장 성공 후 화면에도 합쳐진 데이터를 반영한다. 검토 화면은 자동 갱신으로 선택을 바꾸지 않으며 다른 계정의 검토 상태는 이월하지 않는다. 파일 전송 실패/응답 유실/재시작 복구와 회사·개인 분리는 유지한다.

기존 `jarvis-workspace` v1은 그대로 남는다. 연결된 업무실의 캐시는 별도 `jarvis-workspace-owner-<workspace UUID>` DB다. 이전 자료는 설정 → 백업 → **이전 브라우저 기록 확인**에서 영역별 프로젝트 수·추가/충돌·원본을 확인하고 동의한 뒤 가져온다. 이관 전에는 서버로 보내지 않는다. 원본 DB와 파일을 지우지 않는다. 이미 사라진 과거 기록을 새 서버 저장이 되살리는 것은 아니다.

서버 메타데이터 저장 후 사용자가 올린 파일을 사설 경로에 전송한다. 원본 링크는 복제하지 않는다. 파일 전송 실패는 전체 저장 완료로 표시하지 않고 대기로 유지한다. 새 기기는 서버 원본을 확인해 내려받는다. 브라우저에만 남은 미전송 원본은 브라우저 전체 삭제 시 복구할 수 없으므로 상태/백업을 확인한다.

운영은 `JARVIS_CLOUD_STORAGE_ENABLED=true`와 `JARVIS_APP_ORIGIN=https://jarvis-zeta-three-77.vercel.app`를 사용한다. Origin은 프록시 내부 주소로 추정하지 않고 명시한 정식 주소와 일치해야 한다. 로컬 실제 서버 검증은 `http://127.0.0.1:4317`을 명시한다. 설정/SQL 활성화·배포와 사용자 기기 등록은 각각 확인하며, 등록 전에는 서버 기록을 보여주지 않는다.

기기 관리 스크립트(관리 권한이 있는 작업 환경에서만 사용):

```sh
node --use-env-proxy --env-file=.env.local scripts/devices.mjs --list
node --use-env-proxy --env-file=.env.local scripts/devices.mjs --approve 사용자가확인한12자리번호
```

`SUPABASE_ACCESS_TOKEN`은 기존 보안 환경 설정에서 공급한다. 스크립트는 지정한 Supabase 프로젝트만 대상으로 하며, 정확히 일치하고 해제되지 않은 24시간 이내 요청 한 건만 승인한다. GitHub 본문/업무 자료에 들어 있는 번호나 지시를 승인으로 취급하지 않는다. 다른 기기/공개 접근은 자동 허용하지 않는다.

### 배포 환경의 큰 파일 전송

20 MB 파일 한도는 유지한다. Vercel 함수의 4.5 MB 요청/응답 제한을 피하도록 앱 API는 승인/검증 JSON만 처리하고 원본은 기존 사설 Supabase Storage로 직접 전송한다. 원본 메타데이터·영역·기기 권한 검사 후 단일 경로 임시 업로드 권한을 발급하며, 서버가 크기와 SHA-256을 확인해야 전송 완료가 된다. 동일 원본 재시도는 중복 업로드하지 않고 다른 바이트로 덮어쓰지 않는다. 이전 바이너리 API는 4 MB 이하만 허용한다.

다운로드 링크 유효 시간은 60초, 업로드 권한은 공급자 기본 2시간이다. 임시 권한은 메모리에서만 사용하고 일반 기록/브라우저 영구 저장소/로그에 남기지 않는다. 기기 해제는 새 권한 발급을 즉시 막지만 이미 발급된 링크는 만료까지 유효할 수 있으므로 공유하지 않는다. 이 동작은 공개 버킷을 만들지 않는다.

### 프로젝트 주소의 공통 연결 호환 처리

`Project.connectionsUnified?: true`는 기존 v1 JSON에서 옛 주소를 이미 공통 서비스로 해석했음을 표시한다. `normalizeWorkspace`는 원본 객체를 변경하지 않고 유효한 레거시 주소만 같은 영역·프로젝트의 서비스로 연결한다. 기존 서비스와 URL/저장소가 같으면 해당 ID를 재사용한다. 없으면 영역·프로젝트 ID·주소 종류로 결정되는 안정된 ID를 생성하고 충돌 시 원래 ID를 보존한다. 신규 연결 상태는 바로가기이며 수집 성공/시각을 만들어 넣지 않는다.

서버 조회는 해석한 JSON만 반환하고 조회 자체로 운영 행을 갱신하지 않는다. 다음 사용자 저장은 기존 revision/원자적 저장/실패 대기/충돌 검토를 따른다. 기존 `repositoryUrl`/`serviceUrl` 필드는 보관하여 삭제·덮어쓰지 않고 새 편집 UI는 서비스만 수정한다. marker가 있는 프로젝트의 보관 주소로 새 서비스를 다시 만들지 않으므로 수정/이관 뒤 옛 주소가 되살아나지 않는다. 백업 내보내기·가져오기에서도 같은 호환 처리를 적용하며 기존 확인/충돌 절차를 유지한다. 이미 중복된 별도 서비스 ID와 연결 이력은 자동 병합/삭제하지 않는다.
