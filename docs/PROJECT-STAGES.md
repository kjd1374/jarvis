# 프로젝트 단계와 기획 공간

## 1단계 구현 범위

새 프로젝트는 아이디어·개발·사용 중 카드로 등록한다. 아이디어는 GitHub/외부 자원 없이 기획안과 구독 CLI 대화로 시작한다. 개발은 기존 흐름을 사용하며 새 자동 준비의 대상은 맥미니다. 사용 중은 이미 운영 중인 서비스 주소를 연결하고 목록 카드에서 바로 연다. 관리 링크는 Jarvis의 주소·기본 정보 편집 화면으로 연결한다.

기존 프로젝트에는 단계를 자동 기록하거나 자료를 이전하지 않는다. 단계가 없는 레코드는 기존 개발 화면으로 해석한다. 개발 작업이 없는 프로젝트는 기획으로 전환할 수 있고 기존 연결·대화·업무를 보존한다. 기획을 마친 뒤 개발을 시작하면 동일 프로젝트의 기획안/버전을 개발 요청 맥락에 포함한다. 저장소가 없으면 맥미니 환경 준비를 요청하고 기존 저장소가 있으면 그대로 개발 요청을 만든다.

## 기획안과 실행 계약

실행기 **2.9.3**은 기획 전용 `reply`/`document` 스키마를 직접 사용하며 로그인·기능 확인 각각 15초, 기획 생성 최대 5분으로 제한한다. 세 단계의 시간 초과 코드를 구분하고 최초 문서는 간결하게 시작하되 기존 결정을 보존한다. 실행 중 heartbeat·취소·임대 검증과 결과 캐시는 유지한다. 기획 화면의 버전은 실제 claim을 보낸 실행기의 관찰값이다. 웹 배포와 Mac 적용은 별개이며, 기존 감독기는 작업·활성 미리보기 사이 유휴 시 최대 30분 주기로 업데이트를 확인한다. 과거 실패 요청은 자동 재실행하지 않는다.

`Project.planning`은 현재 문서, 최근 20개 이전 문서, 최대 100개 요청을 보관한다. 문서 최대 16000자, 요청 4000자, 답변 6000자다. 사용자는 직접 편집하고 과거 버전을 열람할 수 있다. AI가 반환하는 것은 답변과 전체 갱신 문서다. 시장 정보의 외부 조회는 이번 경로에 포함하지 않으며 미확인 내용을 가정으로 구분하도록 요청한다.

구독 CLI는 도구·웹·파일 접근이 없는 기존 completion 경로로 실행한다. GitHub 저장소 생성·checkout·모델 도구 실행 없이 승인된 영역/프로젝트의 기획만 수행한다. 실행기 **2.8.0**은 `planningVersion:1`을 광고하고 `/api/automation/planning`으로 heartbeat·결과를 보낸다. 이전 실행기는 기획 요청을 가져가지 않으며 요청은 보관된다. 기존 자동 업데이트의 적용 조건은 유지된다.

요청은 소유자 기기 인증·영역·프로젝트·임대 토큰·만료·취소로 제한된다. 연결된 브라우저의 취소·재시도는 서버의 현재 요청 상태에 명령으로 적용해 heartbeat와 전체 문서 저장의 경합을 피한다. 완료 응답 재전송은 새 문서 버전을 만들지 않는다. 결과 전송만 실패한 같은 실행 시도는 비공개 로컬 캐시를 재사용한다. 백업 복원은 대기/실행 중 기획을 멈추고 재개 전 확인 상태로 둔다.

사용자가 저장한 문서 버전이 AI 작업 시작 시점과 같을 때만 AI 문서를 자동 반영한다. 직접 편집으로 버전이 바뀌면 답변과 제안을 보관하고 사용자가 비교 후 적용한다. 문서 저장과 제안 적용은 현재 버전을 다시 확인한다. 기기 간 서로 다른 문서 편집은 전체 문서 단위 충돌로 보존하며 임대/결과 필드를 섞지 않는다.

## 검증

- 도메인: 단계 등록·기존 자료·범위 제한·중복 제출·임대·취소·버전 편집·제안 적용·개발 맥락·복원·기기 간 병합.
- 실행기: 실제 completion 계약, 도구 비활성, 결과 전달 재시도/캐시, 실패·취소. 모델 결과는 합성이다.
- 데스크톱/모바일: 등록 카드, 직접 편집, 저장·새로고침, 기획 요청, 제안 비교·반영, 개발 전환, 서비스 바로가기와 주소 관리.
- `test:server`: 실제 로컬 Auth/소유자 DB와 브라우저에서 생성→구버전 역량 차단→실제 claim→합성 모델→실제 report→동시 직접 편집 보존→제안 적용→새로고침→개발 전환을 검사한다. 외부 자원 생성과 유료 모델 호출은 하지 않는다.

사용자 Mac의 2.8.0 적용과 실제 구독 기획 응답은 코드/합성 검사와 별도 확인한다.

## 2단계 구현 (Issue #72)

**개발 화면·로컬 서버 관리·수정 및 테스트 흐름**: 실행기 2.9.0은 macOS 격리 로컬 프로세스를 기본으로 사용한다. 같은 SHA·AI 설정의 응답 중인 서버와 의존성을 재사용한다. 데스크톱 화면·대화, 모바일 화면/대화/검사 탭, 서버 재시작·종료·로그, 실제 사진 CLI 입력과 검사 결과를 연결한다. 기존 승인 기기 HTTPS 경로에 제한된 iframe·WebSocket 중계와 Quick Tunnel의 SSE 제한을 피하는 인증된 스트림 조회를 제공하며 새 탭 열기를 유지한다. 기존 Docker 데이터는 이관 확인 전 새 빈 데이터로 실행하지 않는다. 자세한 제한은 ENGINEERING-DECISIONS.md를 따른다.

운영 전환/신규 Vercel·Supabase 연결은 후속 **3단계**다. 사용자 Mac의 2.9.0 적용과 실제 서비스/마이크 동작은 합성 테스트·배포 확인과 별도다.

## 3단계 구현 (Issue #74)

운영 구성 검사·클라우드 배포·DB 준비/재사용·운영 응답 확인·사용자 기능 확인·사용 중 전환과 개발 복귀를 제공한다. GitHub Actions의 제한된 워커가 서버에 저장된 작업을 이어가므로 배포는 맥미니/브라우저 수명에 의존하지 않는다. 추가 맥미니 업데이트는 없다. 코드/서비스별 지원 범위·자원과 데이터 경계·검증은 [PROJECT-OPERATIONS.md](PROJECT-OPERATIONS.md)를 따른다.
