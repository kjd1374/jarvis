# 프로젝트 자동 준비와 대화 개발 — 실행기 2.6.0

Issue #62의 사용자 요청: 맥미니에 반복 접속하지 않고 Jarvis에서 프로젝트 등록, 필요한 GitHub/실행 환경 준비, 대화를 통한 구현·검증·화면 확인을 이어간다.

## 사용 흐름

1. 프로젝트 만들기의 **저장소·실행 환경 자동 준비**는 기본 선택이다. 설명은 첫 개발 요청이며, 명시된 검증 후 병합 범위로 실행한다. 설명 없이 만들면 기본 실행 환경과 화면을 먼저 준비한다. 기존 저장소를 직접 등록하려면 체크를 해제한다. 기존 프로젝트는 **자동으로 개발 환경 준비**로 시작할 수 있다.
2. 관리 프로젝트의 개발은 환경을 준비한 2.6.0 이상 실행기에 고정해 다른 기기의 별도 데이터로 바뀌지 않게 한다. 설치된 실행기 2.6.0은 해당 회사/개인 영역에서 새 프로젝트를 발견한다. 먼저 비공개 저장소, 초기 Node 웹 코드, 실제 실행 가능한 테스트를 만든다. 기존 저장소가 연결되어 있으면 생성하거나 덮어쓰지 않는다.
3. 준비 중 보내는 요청도 보관한다. 준비 완료 후 같은 저장소의 개발 대화로 넘겨 차례로 실행한다. 추가 요청은 최신 미병합 수정본을 이어 쓸 수 있다. 기본 브랜치를 명시한 요청은 유지한다.
4. 수정 → 격리된 실제 테스트 → PR → GitHub에 기록된 검사 상태와 기존 보호 규칙 확인 → 선택한 병합 → 배포 또는 인증된 맥미니 화면 순서다. 자동 준비 프로젝트는 실제 격리 테스트 결과를 정확한 커밋의 `jarvis/isolated-tests` 상태로 게시한다. GitHub Actions 추가 권한을 요구하지 않으며, 기존 외부 검사와 보호 규칙은 계속 적용한다. 모델의 성공 주장으로 검사 결과를 대신하지 않는다.
5. 준비 단계·개발 대화·검사 결과·PR·화면은 프로젝트에 남는다. 실패·취소·재시도와 이전 결과를 구분한다. 자동 준비 재개는 동일 기기와 영속 작업 기록으로 기존 자원을 재사용하며, 프로젝트 이름을 변경해도 중복 생성하지 않는다. 백업 복원은 실행을 멈추며 확인 없이 외부 작업을 재개하지 않는다.

## 환경 선택

### 개발 대상 앱의 로그인·권한 기능 (실행기 2.9.5)

보낸 수정 요청 또는 **기획안을 구현하는 개발 전환 요청**에는 해당 앱의 요구 기능을 구현하는 범위가 포함된다. 로그인·세션·역할·접근 제어 소스와 마이그레이션 파일 작성, 격리된 임시 합성 데이터로 허용/거부 검사를 할 수 있다. 별도의 권한 해제 요청은 필요 없다. 역할이 모호하면 가정과 남은 결정을 기록하고, 서버에서 접근을 검증하며 기존 데이터·보호를 유지한다. 질문 요청은 읽기 전용이다.

실제 인증정보·세션·고객 자료 접근, Jarvis 자체 기기 승인·소유자/영역 격리·실행기 보호 변경, 기존 외부/운영 DB와 서비스에 대한 마이그레이션·계정·RLS·접근 정책 적용은 이 구현 범위와 다르다. 외부 활성화가 필요한 경우 구현 가능한 로컬 코드와 적용 대기를 구분한다. 실행기 갱신 후 새 요청부터 지침이 적용되며 과거 결과를 자동 재실행하지 않는다.

2.9.4에서 앱 권한 구현을 허용했고, 2.9.5부터는 그보다 오래된 실행기에 수정 요청을 넘기지 않는다. 적용 대기 중에는 요청·시도 횟수·기존 결과를 보존하며 미리보기의 서버 종료는 계속 사용할 수 있다. 상단 버전은 최근 접속 정보이며 요청별 실행 버전과 다르다. 과거 버전 미기록은 그대로 표시한다. 과거 답변이 ‘인증·접근 정책 변경 금지’를 현재 제한으로 잘못 인용하면 같은 요청·폴더·격리·게시 범위에서 한 번만 보정한다. 진짜 인증정보 부족·운영 DB 정책 적용·질문 모드는 대상이 아니며 반복 충돌은 `cli_policy_conflict`로 중단한다. 이미 미완료로 끝난 수정 요청은 **미완료 요청 이어서 구현**으로 원래 내용·첨부·범위를 새 요청으로 보낼 수 있다. 이전 미반영 코드를 보존한 PR이 있다고 추정하거나 과거 답변만으로 구현 완료를 주장하지 않는다.

자동 선택은 요청 설명, 필요한 데이터 저장, 연결된 계정의 실제 접근/무료 범위를 확인하는 규칙을 사용한다. AI가 외부 계정 권한이나 과금 범위를 추측하여 확대하지 않는다.

- **맥미니**: 클라우드 계정이 없거나 CLI·상시 서버·렌더링 등 서버 기능이 필요할 때 선택한다. 기본 Node 앱과 필요 시 `node:sqlite` 연결 모듈을 만든다. 앱이 `process.env.DATA_DIR`에 쓰는 데이터는 프로젝트·영역·저장소별 Docker volume에 보관하며 코드 수정/컨테이너 교체 후에도 유지한다. 이전 수동 등록 앱의 임시 데이터 모드는 바뀌지 않는다. 이 volume은 자동 클라우드 백업이 아니다.
- **Vercel**: 연결된 무료 Hobby 계정에서 적합한 웹 앱을 선택한다. GitHub 연결 프로젝트, 보호 설정, 최초 배포 요청을 만든다. 배포 요청과 성공을 구분한다. GitHub 연동 앱이 새 비공개 저장소를 읽을 수 있어야 한다.
- **Supabase**: Vercel 앱에 영속 저장이 필요하고 무료 조직이 연결되어 있으면 새 프로젝트, RLS가 켜진 서버 전용 key/value 저장 테이블, 서버 함수와 저장 모듈을 준비한다. 서버 연결 키는 Vercel의 암호화 환경변수로 전달한다. 앱 사용자별 인증·권한 및 다른 스키마는 해당 개발 요청의 구현/검증 대상이며 자동 준비만으로 완료했다고 하지 않는다. 맥미니의 네트워크 격리 모드에서는 Supabase 대신 SQLite를 사용한다.

Supabase의 `plan` 생성 인자는 현재 공식 API에서 무시되므로 과금 방지 수단으로 사용하지 않는다. 생성 전에 조직 상세의 `plan=free`를 확인한다. Vercel도 실제 Hobby 범위를 확인한다. 한도 초과나 권한 부족 시 기존 자원과 기록을 유지하고 중단하며 유료 플랜으로 변경하지 않는다. 클라우드 계정은 프로젝트의 **클라우드 계정 연결**에서 한 번 연결하고 같은 영역에서 재사용한다. 개인/회사 계정 연결은 별개다.

관리 토큰은 웹 요청으로 서버에 전달한 뒤 AES-256-GCM으로 암호화한다. 암호화 레코드는 소유자·영역·공급자에 바인딩하고 기존 개인 저장소에 보관한다. 관리 키는 모델 프롬프트·Git·일반 백업에 포함하지 않는다. 승인된 실행기의 임대 작업에만 복호화하여 전달한다. 앱 전용 Supabase 키는 실행기의 권한 제한 작업 기록과 Vercel 환경에만 보관한다. 일반 업무 저장 API는 연결 정보를 임의 교체하거나 오래된 브라우저 값으로 되돌리지 않는다. 서버 암호화 기준 키 변경 시 계정을 다시 연결해야 한다.

## 한 번 업데이트한 이후

이번 업데이트는 최신 `jarvis-mac.mjs`의 `update`를 한 번 실행해야 한다. 기존 승인·회사/개인 설정·작업 기록을 재사용한다. 이후 LaunchAgent가 감독 프로세스를 실행한다.

- 개발 작업과 활성 화면이 없는 시점에 약 30분 간격으로 같은 Jarvis 주소의 신규 2.x 버전을 확인한다.
- 별도 디렉터리에 모든 런타임 파일을 받은 뒤 해시·파일명·자체 시작 검사를 통과해야 전환한다. 미래의 같은 규칙을 따르는 추가 모듈도 함께 받는다. 다운그레이드와 다른 major 자동 전환은 거부한다.
- 새 실행기가 기존 기기 인증으로 시작된 것을 확인하기 전까지 이전 경로를 보관한다. 시작 실패 시 이전 실행기로 돌아간다. 전환 도중 감독 프로세스가 종료되면 다음 시작에서 미확인 버전을 되돌린다.
- 다운로드/검증 실패는 현재 버전의 작업을 중단하지 않는다. 기존 검증된 터널 실행 파일을 재사용한다.

Mac 전원, 사용자 로그인, Docker 및 구독 CLI의 최초 인증은 여전히 필요하다. 전원 꺼짐·사용자가 인증을 해제함·외부 공급자 장애를 업데이트로 없앨 수 있다고 표현하지 않는다. 일반 프로젝트 생성/개발/테스트/화면 재준비는 Jarvis 브라우저에서 한다. 화면 HTTPS 연결은 기존 2시간 세션이며 Jarvis에서 다시 준비할 수 있고 프로젝트 데이터는 유지된다.

원격 화면 주소의 DNS 확인에 실패하면 기존 연결을 닫고 새 주소로 한 번 자동 복구한다. 새 주소도 실제 HTTPS 응답을 확인해야 준비 완료가 된다. 취소·인증서 오류·화면 만료 임박은 재발급 대상이 아니며, 공급자 장애가 계속되면 실패 원인을 남기고 중단한다.

## 검증과 경계

필수 `test:server`는 수동 등록 경로에 더해 `tests/support/autopilot-lifecycle.mjs`를 실행한다. 실제 브라우저 생성 → 실제 private 서버/Auth/lease → 합성 GitHub 생성 API로 로컬 Git 저장소 구성 → 실제 체크아웃 → 합성 모델의 실제 파일 수정 → 실제 Docker 테스트 → 실제 검사에서 생성한 커밋 상태/PR/병합 계약 → 실제 서명된 HTTPS 화면 → SQLite 저장 → 후속 수정 → 새 컨테이너에서 값 유지까지 한 흐름이다. 외부 GitHub 쓰기/모델/Cloudflare 전송만 합성이다.

별도 단위/도메인 검사는 부분 생성 재개·이름 변경·중복 결과·취소·다른 기기/영역·암호화 위변조·백업 중단·무료 클라우드 생성 계약·관리 키 비노출·업데이트 무결성·실제 자식 프로세스의 시작 실패 복구를 검사한다. 기존 모바일·저장·격리 실행·실제 Linux/macOS 공급자 검사를 유지한다.

이 검증은 실제 사용자의 Mac 업데이트·실제 Codex 구독 응답·실제 새 Vercel/Supabase 자원의 생성 성공을 대신하지 않는다. 운영 계정/저장소/유료 모델을 CI 재료로 쓰지 않는다. 실제 적용 상태는 프로젝트의 실행기 버전, 준비 결과, 실행한 검사와 화면 결과로 판정한다. 모든 언어/프레임워크/기기 API를 자동 지원하거나 일반 Codex의 모든 기능과 같다고 주장하지 않는다.


## 상태 질문과 현재 기획안 구현 (2.9.6, Issue #90)

CLI 결과 스키마의 action=answer/edit는 현재 사용자 요청을 구분한다. ask는 항상 읽기 전용이다. change의 answer 결과도 게시·검사·미리보기를 시작하지 않는다. 이전 cached receipt의 action 생략은 호환 처리하지만 새 CLI 스키마에서는 필수다. 모델이 답변 중 실수로 로컬 파일을 수정해도 게시하지 않는다. 답변 완료는 해당 질문의 업무에만 반영한다.

“현재 기획안 구현 계속”은 최신 상태 질문 복사가 아니라 명시적 구현 지시로 새 요청을 만든다. 현재 영역·프로젝트·저장소를 검사하며 반영 범위, 요청 ID 중복 방지, 최신 미병합 PR 선택, 기획안 컨텍스트, 기존 이력과 lease fence를 보존한다. 기획안이 없는 경우에만 원래 미완료 요청의 정확한 재실행을 제공한다. 이 기능은 GitHub에 게시하지 않은 임시 구현을 복원했다고 주장하지 않는다. 실제 기본 브랜치·PR의 코드와 과거 답변은 구분한다.
