# v4 읽기 연동 검토

2026-10-15(한국시간). 사용자가 제공한 주소를 확인했다.

- 소스: https://github.com/kjd1374/33m2-v4-workspace
- 웹: https://33m2-v4-workspace.vercel.app
- 검토한 main: `939c9060d8625f55048f939a901c9a8fe25bcedd`
- 범위: 소스/문서 읽기와 비로그인 웹 진입 확인. v4 코드·DB·인증·연결 키·수집기·배포는 변경하지 않았다. 운영 고객 자료/API는 조회하지 않았다.

## 이 주소가 필요한 이유

앞서 v4를 첫 읽기 연동 대상으로 검토하기 위해 저장소 또는 API 문서 주소를 요청했다. Jarvis는 회사 업무실에서 v4의 진행 상황·결과·후속 할 일을 모아 보여주고, 필요한 작업은 v4를 열어 수행하게 한다. 향후 AI도 허용된 회사 자료를 근거로 답하도록 한다.

GitHub는 데이터 구조·API·인증·갱신 방식을 확인하는 곳이다. 실제 업무 자료는 v4의 Supabase Postgres에 있으며 GitHub 주소로 최신 고객 결과를 읽을 수는 없다. 웹 주소는 서비스 열기와 원본으로 돌아가기의 기준 주소다. 자동 업데이트에는 별도의 인증된 읽기 연결이 필요하다.

## 확인한 구조와 재사용할 부분

Next 16.3.4 / React 19.2.6 / Supabase Auth+Postgres를 사용한다. 현재 운영 저장 구조는 `server/database.ts`와 `supabase/migrations/`이며 이전 `db/`·`drizzle/`·D1 예제를 연동 대상으로 사용하지 않는다. Jarvis로 v4 UI·DB·로컬 실행기를 옮기지 않고 v4가 필요한 결과를 제공하게 한다.

문의의 sourceRemoved, 고객/상담의 보관 상태, 통화 집계 제외는 서로 다른 상태다. 보관·집계 제외를 원본 삭제로 해석하지 않는다. 데이터가 발생한 시각(occurredAt), v4에서 바뀐 시각(updatedAt), Jarvis가 읽은 시각(collectedAt)도 분리한다.

성과 집계는 새로 복제 구현하지 않는다. v4의 실제 기간 활동·유입 고객 전환·월 귀속 실적과 KST/다음 달 7일 인정 규칙을 그대로 유지한다. 숫자에는 집계 종류·기간·분모·기준 시각을 함께 제공한다.

`owner()`는 Supabase 세션의 소유자를 확인한다. Jarvis의 로그인이나 Vercel 보호 로그인이 곧바로 v4의 이 세션을 대신하지 않는다. 현재 장치 역할은 lookup/summary/importer/sms이며 Jarvis 전용 reader 역할은 없다. 비공개 DB를 공개 Data API에 노출하거나 DB 쓰기 자격 증명을 Jarvis로 복사하는 방식은 사용하지 않는다.

## v4에 제안하는 최소 변경 — 아직 적용하지 않음

1. **읽기 전용 장치 역할**을 기존 장치 인증 체계에 추가한다. 예시 이름은 `jarvis-reader`이며 아직 존재하지 않는다. 장치 발급 API/화면과 `devices_role_check`의 추가 마이그레이션이 대상이다. 기존 role과 owner 제한은 유지하고, 이 역할은 기존 업로드·저장·문자·요약 실행 API에서 거부되게 한다. 키는 서버 보안 설정에만 보관하고 발급·폐기·접속 확인을 기존 방식으로 재사용한다.
2. **최소 필드 읽기 endpoint**를 추가한다. 경로 예시 `GET /api/integrations/jarvis`는 제안이며 현재 코드에 없다. 기존 records/집계/수집 상태 함수를 재사용해 진행·성과·후속 연락·수집 오류를 제공한다. 첫 범위는 이름/전화번호/통화 전문 전체 대신 원본 ID·상태·기한·허용된 요약·집계·링크로 제한한다. 반환 필드는 구현 전에 확정한다.
3. **완전 수집·갱신 계약**을 명확히 한다. 원본 key/version/updatedAt, 응답 기준 시각/revision, 완료 여부와 수집 오류를 포함한다. 초기에는 제한 내 완전 snapshot을 사용하고 부분/실패 응답은 완전으로 표시하지 않는다. 규모가 커지면 안정적인 snapshot/cursor와 pagination을 추가한다. Jarvis는 모든 페이지를 확인한 후 반영하고 중간 실패를 빈 데이터/삭제로 처리하지 않는다.
4. **개별 항목 바로 열기**가 필요하면 URL로 고객/문의/통화를 선택하는 처리를 추가한다. 현재 workspace는 탭·고객을 React 상태로 선택하며 해당 query/hash 선택 처리는 찾지 못했다. 지금은 서비스 루트 열기가 가능하고, 세부 링크는 추가 구현 대상이다. URL은 항목 ID만 포함하고 고객명·전화번호·세션/토큰을 담지 않는다.

이 변경은 v4 별도 작업/검토 대상으로 먼저 제안한다. 기존 고객 DB 초기화·원본 재가져오기·윈도우 조회기/맥 실행기 수정·자동 작업 실행·양방향 동기화는 필요하지 않다. 새 읽기 역할과 운영 마이그레이션/키 활성화는 별도 승인 전에 실행하지 않는다.

## Jarvis 쪽에서 이어질 작업

- v4를 회사 프로젝트의 서비스로 등록하고 웹 열기를 연결한다. 개인 영역에 등록/검색/AI 전달하지 않는다. v4는 자체 프로젝트 ID가 없으므로 첫 단계는 하나의 Jarvis 회사 프로젝트에 매핑한다.
- v4의 승인된 읽기 계약과 서버 전용 권한이 준비되면 read-only adapter를 작성한다. 현재 registry는 null이며 실제 수집은 아직 미연결이다.
- key를 externalId로, envelope.updatedAt을 sourceUpdatedAt으로, Jarvis 조회 시각을 collectedAt으로 저장한다. version은 충돌·변경 검증 메타데이터로 보존한다.
- v4 수동 내용·AI 요약·외부 요약·원본 사실의 provenance/sourceHash를 구분한다. 현재 Jarvis SourceRecord는 수집 자료를 사실로 표시하므로, 통화 AI 요약을 가져오기 전에 종류/표시 계약도 보강해야 한다.
- Jarvis가 방금 읽었어도 v4의 원본 수집이 오래됐거나 실패했다면 그 상태를 함께 표시한다.
- Jarvis 운영 서버 저장/계정 연결은 아직 비활성이다. v4 API가 생기는 것과 Jarvis 운영 연결 완료는 별개다.

## 검증과 남은 확인

원격 main 접근과 위 코드/스키마/인증/집계/상태 구조를 정적으로 확인했다. 익명 HEAD 요청은 `/login`에서 HTTP 200으로 응답했다. 이는 웹 진입/로그인 화면 확인이며 고객 데이터 조회 성공이 아니다. 웹 배포가 검토한 Git commit과 동일한지까지 검증하지 않았다.

v4 설치 스크립트·테스트·앱·조회기·DB 작업은 실행하지 않았다. 코드 변경 없이 구조만 검토했고 운영 인증/고객 데이터 접근은 범위 밖이므로, npm test나 실제 연동 성공으로 보고하지 않는다. 새 읽기 API를 구현할 때에는 합성 PGlite로 reader의 쓰기 거부, 최소 필드, 원본 ID 중복/변경/보관, 불완전 응답·재시도, 원본 수집 오류, 출처 종류와 KST 집계 의미를 검증해야 한다.
