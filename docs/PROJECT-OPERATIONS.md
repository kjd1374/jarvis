# 개발 완료와 클라우드 운영 전환 (Issue #74)

운영 전환은 개발 코드가 이미 GitHub 기본 브랜치에 있는 경우 실행한다. 새 프로젝트의 기획·CLI 개발은 1·2단계이며 맥미니에서 계속할 수 있다. 3단계의 배포 실행은 맥미니에 의존하지 않는다. 이번 웹 변경은 실행기 버전을 올리지 않는다.

## 사용자 흐름

프로젝트의 **개발 완료·운영 전환**에서 운영 구성을 검사한다. 같은 영역에서 GitHub와 Vercel을 한 번 연결하고 DB가 필요한 경우 Supabase를 연결한다. 기존 암호화 연결은 재사용한다. 자동 선택은 코드의 DB 의존성과 마이그레이션, 이전 연결 ID를 확인한다. GitHub와 같은 저장소에 연결된 Vercel 환경이 하나면 재사용한다. 기존 환경의 DB를 모르는 경우 빈 DB로 대체하지 않고 선택을 요청한다. 여러 배포 환경이 있으면 명시한 환경만 사용한다.

계정 연결은 기존 승인 기기의 UI에서 한다. 토큰은 비밀번호 입력으로 받고 서버에서 암호화하며 AI·소스·워크플로로 전달하지 않는다. GitHub fine-grained 토큰은 대상 저장소의 Contents/Checks 읽기와 Jarvis 저장소의 Actions 실행 권한이 필요하다. 다른 소유자/조직을 함께 사용하면 그 범위를 지원하는 토큰 및 조직 승인이 필요하다. Vercel GitHub 앱에도 대상 저장소 접근을 허용해야 한다. 플랫폼 개발 환경의 인증을 사용자 앱으로 복사하지 않는다.

검토 화면에는 고정 SHA·프레임워크·DB 범위·SQL 파일/hash·실제 GitHub 검사 근거를 표시한다. 진행 중/실패한 GitHub 검사는 배포를 막는다. 자동 검사 근거가 없으면 없다고 표시한다. 사용자가 코드·무료 계정·DB 범위와 별도 운영 환경 시작을 확인한 경우에만 자원을 만든다.

작업은 승인 기기/프로젝트에 묶인 서버 기록에 저장하고 GitHub Actions의 기존 공개 Jarvis 저장소에서 계속한다. 브라우저를 닫거나 맥미니를 꺼도 진행한다. 워커는 앱을 체크아웃하거나 실행하지 않는다. 서버가 제공자 API를 호출하며, 실제 빌드는 Vercel이 고정 SHA로 수행한다. 호스팅 가입/기기 승인/유료 API 모델을 자동 생성하지 않는다.

Vercel READY만으로 완료 처리하지 않는다. 프로젝트 ID·커밋·운영 alias와 HTTP 응답을 확인한 뒤 사용자가 주요 기능과 데이터 저장을 직접 확인하고 **개발 완료 · 사용 중으로 전환**을 누른다. 목록 카드는 서비스 주소로 바로 이동하며 상세 관리에서 수정 개발로 돌아갈 수 있다. 운영 환경은 유지하고 기존 기획·개발 대화·검사·자료를 보존한다. 재배포는 새 구성을 다시 검사한다.

## 지원과 데이터 경계

루트의 Next.js, Vite, Express, 정적 웹을 지원한다. 임의의 장기 실행 Node 서버, SQLite, DATA_DIR 파일 저장, 맥미니 구독 CLI 의존은 서버리스와 같지 않다. 소스에서 발견하면 필요한 변환을 안내하고 성공으로 표시하지 않는다. 로컬 원본/SQLite는 맥미니를 꺼 둔 상태에서 읽을 수 없으며 자동 이관하지 않는다. 기존 자료는 그대로 남고 새 환경은 별도다. 기능/DB 전환 코드는 개발 대화에서 검증해야 한다.

새 무료 Supabase 프로젝트에만 선택한 Git 커밋의 `supabase/migrations/*.sql`을 적용한다(최대 30개/합계 300 KB). 적용은 하나의 DO 트랜잭션, advisory lock, 파일별 hash 이력으로 묶으며 응답 유실 뒤 같은 SQL을 중복 실행하지 않는다. 트랜잭션 안에서 실행할 수 없는 마이그레이션은 실패를 표시한다. 마이그레이션이 없으면 새 DB를 만들지 않는다. 기존 DB는 조직/상태만 확인하고 스키마·업무 자료를 수정하지 않는다. 이후 운영 DB 변경은 별도 검토가 필요하다.

연결은 SUPABASE_URL·publishable/anon key와 프레임워크의 공개 환경변수를 사용한다. 관리 API 토큰과 service_role은 배포된 앱에 주입하지 않는다. 필요한 RLS·앱 인증과 다른 외부 환경변수는 실제 앱의 검증 조건이다. Vercel의 기존 접근 정책은 변경하지 않는다. 자동 HTTP 확인이 접근 보호(401/403)나 정상 이동(30x)으로 제한되면 자동 기능 성공으로 표시하지 않는다. 운영 화면을 연 사용자가 기능을 직접 확인하면 기존 접근 정책을 유지한 채 완료할 수 있다. 5xx 등 실제 오류는 배포 실패로 남긴다.

무료 Vercel Hobby 계정/팀과 무료 Supabase 조직을 매 단계 확인한다. 계정 ID·조직·저장소·프로젝트 바인딩이 바뀌면 중단한다. 무료 한도 부족은 오류로 표시하고 유료 업그레이드·더 큰 실행기를 선택하지 않는다. GitHub 워커는 기존 공개 저장소의 표준 ubuntu-latest이며 최대 30분, 승인 티켓은 25분이다.

## 실패·재개·권한

각 외부 생성 전에 서버에 의도를 기록한다. 응답을 잃으면 정확한 자원 이름/조직/작업 메타데이터로 조회한다. 결과를 확인하지 못하면 중복 POST를 하지 않고 검토 상태로 남긴다. 취소/재시도는 실행 nonce를 바꿔 과거 워커를 차단한다. 단계별 CAS 임대는 중복 워커가 동시에 진행하지 못하게 하고, 모든 제공자 호출 전 현재 요청·저장소 연결·제공자 봉인을 재확인한다. 이미 진행 중인 외부 요청이 완료될 수 있으므로 취소는 자원 삭제를 뜻하지 않는다.

워커는 GitHub OIDC의 서명·audience·저장소·main 워크플로·실행 ID도 검증한다. 공개 작업 입력의 grant만 복사해서는 실행할 수 없다. 입력은 GITHUB_EVENT_PATH에서 읽어 환경변수 출력으로 노출하지 않는다. 워크플로에는 관리 토큰 대신 암호화된 한 작업용 grant를 전달한다. 원래 승인 기기의 단기 인증은 서버에서만 복호화해 현재 기기 승인을 다시 검사하며 다른 프로젝트/영역으로 바꿀 수 없다. 재개는 새 grant를 발급한다. 원본 티켓과 인증은 로그·프로젝트 기록에 저장하지 않는다. 워커는 일시적 통신 실패를 제한적으로 재시도하며 권한 거부는 즉시 멈춘다. 시간이 만료되면 UI의 상태 검사에서 실패를 기록하고 기존 자원으로 재개할 수 있다.

일반 브라우저 저장은 배포 결과/임대/자원 ID를 작성하지 못한다. 오래된 저장과 충돌 검토도 서버 기록을 보존한다. 백업 복원은 새 배포를 시작하지 않으며, 명시적인 복원 중단은 현재 작업을 끊고 재검토 상태로 남긴다. 원본 업무·DB 자동 삭제, 강제 push, 보호 우회, 자동 과금 전환은 없다.

## 검증

`npm run test:release`는 실제 제공자 계약의 합성 응답으로 고정 SHA·무료 범위·DB 생성/재사용·암호 키 경계·서명 입장·취소·응답 유실 및 복구를 확인한다. 외부 자원은 만들지 않는다. 도메인 검사는 완료 기준·영역·기기 간 병합·백업 중단을 확인한다.

브라우저 검사는 데스크톱/모바일의 구성 검사→검토→실행→서비스 기능 확인→사용 중→개발 복귀를 수행한다. `npm run test:server`는 실제 일회용 Supabase Auth/RLS/JSON 저장과 TLS 제공자 fixture, 브라우저 기기 승인, 실제 Node 워커, 별도 임시 PostgreSQL DB의 SQL/RLS/원자성/재시도 보존을 연결한다. 브라우저 종료 뒤 진행과 오래된 grant/취소/기기 해제를 검사한다. 진단 중에는 `npm run test:server -- --release-only`를 사용할 수 있고 CI 기본 검사는 전체 그룹을 실행한다.

실제 사용자 계정의 최초 자원 생성과 서비스별 데이터/AI 동작은 합성 검증과 구분한다. 운영 Jarvis의 배포 SHA·실행기 무결성·공개 웹 파일 검증은 PR에 기록한다. GitHub를 한 번 연결하지 않은 영역은 연결 필요 상태이며 연결된 것으로 가장하지 않는다.
